## 2. Permissions decision: none added

- **Sessions, status, transcript rows, finished subagents and the coarse live
  subagent flags** all come from `/api/chat/slots` and `/api/chat/slots/{key}`,
  already covered by `/api/chat`.
- **Running subagents individually** are only in the task store (`/api/tasks`),
  the result files (`/api/sessions/{id}/agents`) and WS events. Each grant is
  far wider than the need: the SDK fence matches a prefix regardless of
  method, so `/api/tasks` would also admit cancelling and answering any task
  on the gateway, and `/api/sessions` admits session deletion and restart. No
  narrower pattern exists: `/api/sessions/{id}/agents` has the variable in the
  middle, and a `*` prefix like `/api/sessions/dashboard:quartizo-*` would still
  cover `DELETE /api/sessions/dashboard:quartizo-…`. Result files carry no
  status anyway.
- **Events**: declaring `chat_status`, `tool_call`, `subagent_*` etc. would
  deliver nothing to the page in 0.10.0rc4 (the host relays only `slots`), and
  for an app-token socket they would be own-only, which excludes our owner
  sessions. So none are declared. The page subscribes to `slots` (no grant
  required) purely as a hint to poll sooner.

If a later release relays events or adds a narrow per-session subagent route,
adding a grant would disable the app until the user approves it again.

### 3a. Recorded sessions (routes added to Quartizo's own backend)

Not a gateway route and no `app.json` change: Quartizo's backend (already
under the granted `/apps/quartizo/api`) keeps the keys of the sessions the page
created. `openSlot` calls `POST /api/slots` after the gateway returns the key,
for both the Chat tab and each workspace chat, and again on every reopen
(idempotent, so a key stored by an earlier version is recorded too). If the
recording fails, opening the chat fails with the error and the stored name is
reopened (and recorded) next time. Recording is a claim by the page, not by the
gateway: it stops a stray name from being treated as Quartizo's, it does not
authenticate the gateway session itself.

| Route | Auth | Result |
|---|---|---|
| `POST /api/slots {key}` | owner session only | 200 `{slot: {key, workspaceUid, createdAt}}`, idempotent; 400 `bad_slot_key` unless the key matches the UI's slot-name rule (`quartizo-[w<32 hex>-]<time>-<6>`); 404 `workspace_not_found` for an unregistered workspace uid |
| `GET /api/slots` | owner session only | `{slots: [...]}` |

Not built (by scope): stop/cancel from this tab, any write to a session.

## 5. Upstream needs (KiroCrew #9712)

1. **Live streaming to app pages.** The 0.10.0rc4 AppHost relays only
   `mc:app:slots`; `useAppEvents('tool_call' | 'chat_status' | 'subagent_*')`
   never fires in a page whatever the manifest declares. Needed: the host
   relaying declared events, scoped to sessions the page created (owner
   sessions created through the page carry no app ownership today).
2. **Session ownership for page-created sessions.** Owner-cookie creates record
   `app: ""`, so every app-scoped mechanism (WS own-only scope, per-slot
   ownership) treats them as foreign. A way for a page to create sessions
   owned by its app (or tagged with it) would let the gateway, not a name
   pattern, define "Quartizo's sessions", and would let the list be filtered
   server-side instead of returning every session to the page.
3. **Per-session subagent status route** under `/api/chat/slots/{key}/…`
   (id, name, state, started, last tool, tool count, stalled, error), so
   running subagents can be shown without `/api/tasks` or `/api/sessions`.
4. **Tool outcome on transcript rows.** Rows record `done` only; the tool's
   terminal status (`completed` / `failed`) reaches the crew log but not the
   row (`chat_runner.py:11283-11297`).
5. **Method-aware permissions.** `permissions.api` matches path prefixes for all
   methods, so a read grant cannot be separated from cancel/delete on the same
   prefix (`/api/tasks`, `/api/sessions`).
6. **Stop/cancel for apps**: `POST /api/chat/slots/{key}/stop` exists and is
   covered by `/api/chat`; subagent cancel (`POST /api/tasks/{id}/cancel`)
   needs the whole `/api/tasks` grant. A per-session subagent stop route under
   `/api/chat/slots/{key}` would keep it narrow.
7. **Cross-session inspection.** `GET /api/sessions/{id}/agents*` performs no
   ownership check for owner callers and creates nothing per app; any app
   granted `/api/sessions` can read every session's subagent results. A scoped
   variant is needed before granting it.
