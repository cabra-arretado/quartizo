Checked against **kirocrew 0.10.0rc4** (`~/.kiro/crew-venv`). There is no manifest
or permission change. The one backend change is a workspace `uid`, added in the review fixes below.

## Review fixes

| # | Fix |
|---|---|
| 1 | **Id reuse.** Migration 2 rebuilds `workspaces` with `INTEGER PRIMARY KEY AUTOINCREMENT`, so ids are never reused, and adds `uid TEXT NOT NULL UNIQUE`. Existing rows get `lower(hex(randomblob(16)))`; new rows get `secrets.token_hex(16)`. The API returns `{id, uid, name, path}`. The UI keys the chat by `uid`, so a later registration, even one that got an id reused before the migration, never inherits a chat. An older backend without `uid` gets "no chat" instead of a shared one. Removing a workspace clears its stored session key. Tests: `tests/backend/test_workspace.py` (v1 DB migration keeps rows and adds unique uids; ids are not reused; `to_json`), `ui/test/slots.test.ts` |
| 2 | **No orphan slot.** `openStoredSlot` saves a fresh name *before* `POST /api/chat/slots`, so an unmount mid-request reopens the same name next time. A remembered name answered with `slot_not_found` is replaced once by a fresh one |
| 3 | **"Selection → chat"** prefers the pane last used: the textarea when it is focused, or when it was the last pane selected in and has a non-empty selection. Otherwise the preview selection |
| 4 | **Stale context.** Editing the note after a context was picked (preview or attached) drops it, with the notice "The note was edited after the context was picked…". The user picks it again |
| 5 | **Header values** (workspace name, note path) are capped at 256 characters (with `…`). NEL (U+0085), U+2028/2029 and the bidi controls U+202A–202E and U+2066–2069 are also replaced |

## How delivery works

1. **ChatEmbed has no draft prop**, so prefilling the embed is not possible.
   Instead the context is prepended in the existing `onSend` wrapper:
   `attachingSender(createSender(...), holder, workspaceId, onConsumed)`.
   - It acts only when the user attached a context. The message becomes
     `formatContext(ctx) + "\n\n" + message`.
   - After the send resolves, the context is cleared, so it goes with exactly one message.
   - If the send fails, the context stays attached. ChatEmbed restores the typed draft, so a retry carries the same context.
   - A context attached while a send is in flight is not cleared by that send.
   - A context whose `workspaceId` differs from the chat's is refused and dropped. This is defence in depth: the view is per-workspace anyway.
   - **Duplicate on ambiguous retry (accepted).** A send can reach the gateway while its response is lost (network drop, proxy timeout). Quartizo then sees a failure and keeps the context attached, and ChatEmbed restores the typed draft. A retry therefore sends the message, and the context block, a second time. No idempotent-send API is documented, so this is left as is.
   - The "Attached: … Sent with your next message only. Remove" chip is shown through ChatEmbed's `aboveComposer`.
   - Visible side effect: ChatEmbed's optimistic row shows only the typed text (it renders `draftText`). The polled transcript then shows the full message with the block.
2. **Optional handoff to the full chat page.** The preview panel's **Open in
   full chat as draft** calls
   `useChatLauncher().openChat({ slotKey, message: block + "\n\n", autoSend: false })`.
   It always passes `autoSend: false` explicitly, and nothing is sent.
3. Nothing auto-sends and nothing auto-attaches.

## Backend needs

The workspace `uid` and AUTOINCREMENT migration (fix 1) are done. Possible later items:
- **App-owned workspace sessions.** These would need the backend-mediated app-token path noted for QTZ-003. Page-created sessions remain owner sessions, which is the accepted default.
- **Old per-workspace sessions are not deleted.** This covers "Start new chat for this workspace" and removed workspaces. A cleanup would need `DELETE /api/chat/slots/{key}` from the page or a backend job, and it is not built.
